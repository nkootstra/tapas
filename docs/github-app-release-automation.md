# GitHub App release automation

Tapas uses release-plz to prepare version and changelog pull requests and to create signed release tags. The existing tag-triggered CI remains responsible for building checksummed binaries and publishing the GitHub Release.

Merging a release PR is the release approval. Once it reaches `main`, release-plz creates a signed `vX.Y.Z` tag and the regular CI and publishing workflows run.

## Required repository settings

Configure these under **Settings → Secrets and variables → Actions**:

| Type | Name | Value |
| --- | --- | --- |
| Variable | `RELEASE_APP_ID` | Numeric GitHub App ID |
| Secret | `RELEASE_APP_PRIVATE_KEY` | Complete PEM private key generated by GitHub |
| Secret | `RELEASE_SIGNING_KEY` | Complete OpenSSH private release-signing key |

Never commit either private key. Do not paste private keys into issues, pull requests, logs, or chat.

Configure pull request merging under **Settings → General → Pull Requests**:

1. Enable squash merging.
2. Disable merge commits and rebase merging.
3. Set the default squash commit title to **Pull request title**. Always use the pull request title so the validated `major:`, `minor:`, `patch:`, or `skip:` prefix reaches `main`.
4. Protect `main` with **Require a pull request before merging**, **Require conversation resolution before merging**, and **Require linear history**. Apply the rule to administrators. A solo-maintainer repository can require zero approving reviews while still requiring the pull-request path.

These repository settings are required setup and ensure the pull request title becomes the commit subject on `main`. The workflow does not inspect the repository merge settings at runtime. Instead, before calculating a version, it validates the actual merged commit subject and fails closed unless that subject starts with `major:`, `minor:`, `patch:`, or `skip:`. The equivalent GitHub CLI command for configuring the required merge settings is:

```sh
gh api --method PATCH repos/nkootstra/tapas \
  -F allow_squash_merge=true \
  -F allow_merge_commit=false \
  -F allow_rebase_merge=false \
  -f squash_merge_commit_title=PR_TITLE
```

## Create and install the GitHub App

1. Open <https://github.com/settings/apps/new>.
2. Give the App a unique name such as `Tapas Release nkootstra`.
3. Set the homepage URL to <https://github.com/nkootstra/tapas>.
4. Disable the webhook.
5. Grant repository **Contents: Read and write** and **Pull requests: Read and write**. Leave every other permission disabled.
6. Limit installation to the owning account, then create the App.
7. Copy the numeric App ID into the `RELEASE_APP_ID` repository variable.
8. Generate an App private key and store the downloaded PEM as the `RELEASE_APP_PRIVATE_KEY` repository secret.
9. Install the App only on the `nkootstra/tapas` repository.

The App token is short-lived and restricted to this repository. The default workflow token stays read-only.

## Create the release-signing key

Generate a dedicated key that is used only for release signatures:

```sh
ssh-keygen \
  -t ed25519 \
  -C "545768+nkootstra@users.noreply.github.com" \
  -f "$HOME/.ssh/tapas_release_signing_ed25519" \
  -N ""
```

Register only its public half as a GitHub signing key:

```sh
gh ssh-key add \
  "$HOME/.ssh/tapas_release_signing_ed25519.pub" \
  --type signing \
  --title "Tapas release automation"
```

Upload the private half directly to Actions without printing it:

```sh
gh secret set RELEASE_SIGNING_KEY \
  --repo nkootstra/tapas \
  < "$HOME/.ssh/tapas_release_signing_ed25519"
```

The corresponding public key is checked into `.github/release-signers` so CI can verify tags without trusting secret state.

## Release-title policy

Every pull request title must use exactly one release-intent prefix:

- `major:` increments the first SemVer component, including `0.3.0` to `1.0.0`.
- `minor:` increments the second component.
- `patch:` increments the third component.
- `skip:` does not create a release and is omitted from the changelog.

When several pull requests are awaiting release, the highest intent wins. Release-plz maintains one release PR containing the accumulated version, lockfile, and changelog changes.

## Verification and recovery

List configured names without revealing values:

```sh
gh variable list --repo nkootstra/tapas
gh secret list --repo nkootstra/tapas
```

CI verifies the SSH signature and source commit before building or publishing a tagged release. If a tag exists but CI fails, fix the problem in a new pull request and publish a new patch version; do not move or overwrite a published version tag.

To rotate credentials:

1. Generate and register the replacement App or signing key.
2. Update the corresponding repository secret.
3. Update `.github/release-signers` in the same reviewed pull request when the signing key changes.
4. Complete a patch release before revoking the previous credential.
